# Positron Tanks v1 Specification

Positron Tanks is a backend service for programmable robot combat. Players design Bots from a point-budgeted Parts Catalog, program them in a small language, and enter them into fully automatic Games that they can watch but not influence. The API is designed so that LLM agents can play as easily as humans.

Vocabulary follows [GLOSSARY.md](../../GLOSSARY.md). Architectural decisions are in [docs/adr/](../adr/):

- [ADR-0001](../adr/0001-fixed-tick-simultaneous-simulation.md): fixed-tick, simultaneous, deterministic simulation
- [ADR-0002](../adr/0002-counted-operation-budget.md): counted Operation Budget, not a time limit
- [ADR-0003](../adr/0003-single-instance-sqlite.md): single instance, SQLite + Litestream, object storage
- [ADR-0004](../adr/0004-extensibility-through-ruleset-data.md): extensibility through Ruleset-versioned data and engines
- [ADR-0005](../adr/0005-own-deterministic-math-library.md): own deterministic math functions

Two areas are deliberately left to their own design sessions: the **detailed language specification** (grammar, full built-in list, operation costs) and the **starter catalog numbers** (Chassis, Component stats and costs, Terrain multipliers, Point Budget range). This document fixes their structure only; the values are in [language-r1.md](../../packages/ruleset-data/spec/r1/language-r1.md) and [catalog-r1.md](../../packages/ruleset-data/spec/r1/catalog-r1.md).

## 1. Scope

### In v1

- Accounts (username + password), session tokens, API keys
- One initial Ruleset (r1): Parts Catalog, rules, language spec
- The Positron Tanks language: parser, checker, interpreter with Operation Budget
- Garages: Bot Designs and Revisions, copy-to-Ruleset, archiving
- Maps and Map Revisions, including Terrain, Obstacles, Spawn Zones
- Full Game lifecycle with real-time and unthrottled Pace
- Simulation: movement, Terrain, collisions and ramming, Melee/Projectile/Beam weapons, Radar/Rangefinder/Projectile Detector, Armor by side, friendly fire
- Replays, snapshot and SSE spectating, "my Games" endpoint
- CLI runner for local Games without a server
- OpenAPI spec served by the server
- Docker image; Pulumi (TypeScript) for AWS; SQLite + Litestream
- Data fields reserved for images (Player Emblem, Bot Design icon, catalog artwork references and Slot geometry), with placeholder shapes in place of real artwork

### Out of v1 (designed for, not built)

Webhooks · heat management · Component damage · messaging between Bots · OAuth and email verification · Sides/alliances · custom Components · pushable Obstacles · rankings · hazardous Terrain · turret rotation speed · image uploads · a frontend · Azure deployment

## 2. Simulation

Exact movement, collision, ramming and weapon rules for r1: [engine-r1.md](../../packages/ruleset-data/spec/r1/engine-r1.md).

### Time

- The world advances in **Ticks**. Each Ruleset fixes its Tick rate (r1: **10 Ticks per simulated second**).
- Each Tick: every Bot's `tick()` runs against the same world snapshot; then all commands resolve simultaneously; then movement, collisions, projectiles and damage are applied.
- Games are deterministic: a Game Record (Ruleset version, Map Revision, Entries with Programs, starting positions, seed) reproduces the Game exactly. Randomness comes only from the seeded RNG.
- **Pace** (chosen by the Initiator): `realtime` (one simulated second per real second) or `unthrottled`. The server may limit concurrent unthrottled Games.

### Coordinates and units

- Distances in meters, speed in m/s, time in Ticks (seconds available as a convenience).
- Map origin at top-left; x increases rightward, y increases downward (matches SVG).
- Angles in degrees. Absolute Heading 0° = up the Map, increasing clockwise.
- Built-ins taking a bearing use angles **relative to the Bot's Heading** by default, with absolute variants where useful.
- No `Math.sin`/`cos`/`atan2` etc. anywhere in the engine; each engine ships its own pinned implementations (ADR-0005).

### Movement

- Heading-based (tank-style): motors drive forward/backward along the Heading; the Bot turns at a rate determined by its motors, mass, and Chassis. No strafing.
- `throttle` and `turn` commands persist until changed; requests beyond the Build's limits are clamped.
- **Terrain** under the Bot's center multiplies its maximum speed and acceleration (not turn rate). Motor Components may carry per-Terrain modifiers (e.g. tracks vs wheels).

### Collisions

- Bots cannot pass through other Bots, Obstacles, or the Map boundary.
- Collisions deal damage to both parties based on closing speed and mass, reduced by the Armor on the struck side. Ramming is a legitimate tactic, including against Friends.

### Weapons

- Weapons mount in weapon Slots. The **Slot** determines the direction; the **Component** determines Firing Arc width. Turrets are pricier/heavier Components with wide arcs.
- `fire(weapon, target)`, where `target` is a currently sensed Bot or a bearing. Legal only if the target is within the weapon's Firing Arc, the weapon has reloaded, and line of fire is not blocked by an Obstacle. Aim within the arc is instant.
- Categories:
  - **Melee**: contact range, high damage.
  - **Projectile**: travels over several Ticks; can be dodged; hits the first Bot or Obstacle in its path.
  - **Beam**: instant hit along a straight line within range.
- Hits are purely geometric (no random hit chance in r1).
- **Friendly fire**: everything damages whatever it hits, Friend or Foe. A Bot cannot hit itself with its own fire.

### Damage

- Each Chassis has Hit Points; at zero, the Bot is **Disabled**. A Bot whose Program halts (failed `init()` or memory cap exceeded) is also Disabled. A Disabled Bot stops dead and becomes an indestructible wreck Obstacle ([language-r1.md §10.4](../../packages/ruleset-data/spec/r1/language-r1.md#104-disabled-bots)).
- **Armor** is bought per side (front, left, right, rear). The struck side is determined by the angle of impact relative to the target's Heading.
- Destructible Obstacles have their own Hit Points.
- Every damage event records the side struck, the impact point, and the absorbing entity (always the Chassis in r1) for future Component damage (ADR-0004).
- Bots have a "stopped" status distinct from Disabled, unused in r1 (reserved for overheating).

### Sensors and knowledge

- A Bot always knows its own state: position, Heading, speed, Hit Points, reload timers, Operation Budget remaining.
- A Bot receives the full Map (Obstacles, Terrain, boundaries) at Game start.
- Other Bots are known only through sensors. Sensors sit in sensor Slots (direction from the Slot; arc and range from the Component). Obstacles block line of sight.
  - **Radar**: Bots within arc and range: position, Heading, speed, Friend-or-Foe.
  - **Rangefinder**: a single ray; distance to the first thing hit.
  - **Projectile Detector**: only Projectiles on a collision course (would hit this Bot if it stayed still, ignoring who fired them), excluding those that would first hit an Obstacle or another Bot. Reports bearing, Ticks to impact, and weapon category. Beams are undetectable.
- Friend-or-Foe is built in, free, and always correct.
- Terrain lookups (Map knowledge, not sensors, see through Obstacles): `terrainHere()`, `checkTerrain(angle, distance)`, `terrainAt(x, y)`; the Ruleset's Terrain table is readable.

### Win condition

- The Game ends when at most one Player has any Bot not Disabled; that Player is the **Winner**.
- At the time limit with several Players remaining: Winner is the Player whose Bots inflicted the most damage on **Foes** (any source, including ramming; each hit counted only up to the target's remaining Hit Points; damage absorbed by Armor does not count; Friend damage neither counts nor subtracts). Next tiebreak: remaining total Hit Points. Then a **Draw**.

## 3. Bot Designs

- A **Bot Design** = **Build** (one Chassis, Components installed in compatible Slots, Armor per side) + **Program**.
- Authored against one Ruleset version. Validated on save: Slot compatibility, Program syntax and checks, references to unknown Components or built-ins.
- Edits create a new **Revision**; Entries reference a specific Revision.
- **Copy to Ruleset**: copies a design into another Ruleset version, re-validates, and reports problems (over budget, removed Components, unknown built-ins).
- "Deleting" archives: hidden from listings and unusable in new Entries; Revisions used by any Game are never deleted. Unused Revisions may be truly deleted.
- Every Chassis includes a minimal **Processor**; better Processors are Components that raise the Operation Budget.
- A design has a name and a description (see section 9), changeable by its owner at any time without a new Revision.
- Visibility: Programs and descriptions are visible only to their owner, ever. Builds are hidden while a Game is Open and visible to everyone from Running onward.

## 4. The Positron Tanks language (structure only)

Full grammar, built-in list, and operation costs: [language-r1.md](../../packages/ruleset-data/spec/r1/language-r1.md).

- Small, JavaScript-flavored syntax (braces, no significant whitespace).
- Types: numbers (doubles), booleans, strings, lists, records, functions. Control flow: `if`, `while`, `for`. No classes, modules, I/O, or networking.
- Entry points: `init()` once at Game start; `tick()` every Tick. Persistent state lives in top-level variables, subject to a counted memory cap.
- Built-ins are camelCase. Commands: persistent movement commands (`throttle`, `turn`), one-shot actions (`fire`); last-issued wins within a Tick.
- The set of `self.*` values and built-ins is defined per Ruleset.
- **Operation Budget** (ADR-0002): source-level operations counted per Tick; built-ins have documented costs. `budgetRemaining()` exposes the remainder.
- Errors: running out of budget or a runtime error in `tick()` ends that Tick's execution; commands already issued still apply; the error is logged for the owner. Failure in `init()`, or exceeding the memory cap, halts the Program for the Game and Disables the Bot. Most mistakes are caught at save time.
- Deterministic math built-ins (trig, sqrt) come from the engine's pinned library.

## 5. Rulesets and the Parts Catalog

- A **Ruleset** version bundles Parts Catalog + rules + language spec; any change bumps the whole version, with unchanged parts carried forward.
- Each Ruleset version has a **frozen engine** (`engine-rN` package) never edited after release. The server hosts any supported version side by side; nothing is retired by default.
- Component and Chassis definitions are open-ended stat sets (ADR-0004). Components declare Slot type compatibility; Chassis declare Slots (type, position, direction), size, shape, base mass, Hit Points, built-in Processor.
- Each Ruleset declares: Tick rate, allowed **Point Budget range** (which bounds Bots per Entry relative to the cheapest Chassis), Terrain types and multipliers, supported **Map Formats**, Operation Budget and memory rules.
- Catalog entries carry artwork references (top-down SVG) and Slot geometry so a frontend can compose Bot images; v1 uses placeholders.
  - Component SVGs are drawn in meters, with the origin at the Slot, pointing along the Slot direction (up the SVG's -y axis, as the Heading in the Bot frame). Chassis SVGs are drawn in the Bot frame.
  - A Slot-mounted Component may also carry an optional **`visualSize`** `{ length, width }` beside its artwork reference: how big clients draw it, in meters, with `length` along the Slot direction and `width` across it, origin at the Slot (the same convention as its SVG). Both must be finite and greater than 0, and neither may exceed the largest dimension of any Chassis in the same Ruleset (a circle's diameter, or the larger side of a polygon's bounding box); validation rejects anything else. Chassis have no `visualSize` (their simulated shape is drawn), nor does side-mounted Armor.
  - `visualSize` is purely visual. It is not a stat (ADR-0004), no engine reads it, and weapon and sensor range is still measured from the Bot's centre. Overlap between drawn Components, or with other Bots, is acceptable and never checked; the cap only keeps sizes from getting absurd.
- Every Chassis, Component (Armor included) and Terrain carries a required **`description`**: short prose for Players and clients saying what it is and what it is good for. It is plain text on one line: 1 to 500 characters (Unicode code points), with no leading or trailing whitespace and no control characters such as line breaks; it is never interpreted as markup. Validation rejects anything else. Like `visualSize` it is not a stat and no engine reads it, but it is part of the frozen Ruleset data and is served with the Parts Catalog and Terrain table.

## 6. Maps

- A **Map**: rectangular, with boundary walls; **Base Terrain** plus **Terrain Regions** (polygons/circles; later-listed wins on overlap); **Obstacles** (polygons/circles; permanent or destructible with Hit Points); **Spawn Zones** (area, starting Heading, capacity), one per supported Player.
- Versioned by **Map Format**, independent of Rulesets; each Ruleset declares the formats it supports.
- Readable by anyone; editable and archivable only by the creator. Edits create Map Revisions; Games reference a specific Map Revision. The name and public description belong to the Map, not a Revision (see section 9).
- At Game start, each Entry is assigned a Spawn Zone by seeded random draw, largest Entry first, among the free zones whose capacity holds it; its Bots are placed deterministically inside it. An Entry whose Bots would not fit any Spawn Zone's capacity is rejected on submission; Entries are checked one at a time, not jointly. When zone capacities differ, an Entry may find no free zone large enough: it then takes the largest free zone and its Bots beyond that capacity **spill**, placed deterministically at the nearest free spots around the zone, outside every other Spawn Zone. So a Game whose Entries each fit some Spawn Zone always starts, unless the Map itself has no room left for a Bot.

## 7. Games

### Creation

The Initiator chooses: Ruleset version, Map Revision, number of Players (≤ Map's Spawn Zones), Point Budget (within the Ruleset's range), time limit (simulated seconds, ≤ server maximum), Pace, and fill timeout (≤ server maximum). The Initiator need not enter.

### Lifecycle

- **Open**: accepting Entries. Players may withdraw. The Initiator may cancel. Auto-cancelled if not full by the fill timeout.
- **Running**: starts automatically the moment the Game is full.
- **Finished**: ended with a Winner or Draw.
- **Cancelled**: ended without being played: by the Initiator (cancel reason `initiator`), by the fill timeout (`fill_timeout`), or because the server failed to play it (`server_error`, see Resilience). A Cancelled Game has no result or Replay, and its Builds stay hidden.

### Entries

- An Entry is one or more Bot Design Revisions (same Ruleset as the Game), each with a **Bot Name** unique within the Game, whose combined cost is within the Point Budget.
- A Player may submit more than one Entry to the same Game.

### Resilience

On startup, the server resumes every Running Game by replaying its Game Record up to the last persisted Tick and continuing.

If starting, resuming or playing a Game fails (its engine or storage throws), the server retries it with backoff: 3 attempts in total over about a minute, counting attempts made on resume after a restart. After the last failed attempt the Game is Cancelled with cancel reason `server_error`, any partial Game Record, Replay and Program logs are discarded, and the failure is logged.

## 8. Visibility and Replays

- **Game Record**: held only by the server that played the Game; never downloadable. Local reproduction is only possible when you own every participant (via the CLI runner).
- **Replay**: the full event history plus every participating Build (never Programs). Available to anyone after the Game; rewatchable via the API at any time.
- Owners can additionally see their own Bots' Program logs (errors, budget usage).

## 9. API

REST + JSON, described by an OpenAPI document served by the server. Rules, language spec, Parts Catalog, and the OpenAPI document are published per Ruleset version. Each hosted Ruleset version also serves its prose documents (simulation rules, language specification, Parts Catalog and balance) as `text/markdown`: `GET /rulesets/{version}/docs` lists them and `GET /rulesets/{version}/docs/{engine|language|catalog}` returns one. Their single source ships with the Ruleset data in `packages/ruleset-data/spec/<version>/`; links between them are relative to their served paths, so they carry no version or path prefix.

| Area | Endpoints (indicative) |
|---|---|
| Accounts | sign up, log in (session token), create/list/revoke API keys |
| Rulesets | list supported versions; get rules, language spec, Parts Catalog, Terrain table; list/get prose docs (Markdown) |
| Garage | create/list/get Bot Designs; rename/describe (PATCH); create Revision; copy to Ruleset; archive; **check tick cost** of a handler against a sample world (local-server feature, below) |
| Maps | create/list/get Maps; rename/describe (PATCH); create Revision; archive |
| Games | create; browse Open Games (filter by Ruleset, budget, player count, Map); get; submit/withdraw Entry; cancel; "my Games" filtered by state |
| Spectating | snapshot (latest Tick, any authenticated Player); SSE stream (one message per Tick); Replay |

The tick cost check is a local-server feature: it runs a Program for many Ticks synchronously, so only servers that enable it (`POSITRONTANKS_TICK_COST_CHECK=on`, as the local `docker run` instructions in `docs/docker.md` do) serve it; elsewhere, including the AWS deployment, it answers 410 `feature_disabled`. A public `GET /server` reports `{ "features": { "tickCostCheck": true|false } }` so clients and agents can check first.

Names and descriptions:

- Bot Designs and Maps each have a name (1-64 characters, trimmed) and a **description**: plain text, trimmed, 0-2000 characters, empty by default. Both may be given on create and changed with `PATCH /bot-designs/{id}` or `PATCH /maps/{id}` (`name` and/or `description`; fields left out are kept). They belong to the design or Map, not a Revision, so changing them adds no Revision; it updates `updatedAt` and is allowed on archived items too.
- Only the owner (Bot Design) or creator (Map) may change them: another Player gets 404 for a Bot Design, exactly as for any other design request, and 403 `forbidden` for a Map.
- Visibility follows the item: a Map's description is public; a Bot Design's description is private to its owner and never appears in Games, Replays or any other Player-visible response. Copy to Ruleset keeps the source's description.

Revision notes:

- Each Bot Design Revision and Map Revision has **notes**, like a commit message: what changed in it (for a Bot Design, the Build and/or Program). Plain text, trimmed, 0-500 characters, empty by default.
- Notes are given only when the Revision is created (`notes` on creating a design or Map, for Revision 1, and on creating a Revision) and, like the rest of the Revision, can never be changed. They are returned wherever Revisions are, listings included.
- Visibility follows the parent: Map Revision notes are public; Bot Design Revision notes are private to the owner and never appear in Games, Replays or any other Player-visible response. Copy to Ruleset does not copy the source Revision's notes: the new design's Revision 1 takes `notes` from the request, empty if left out.

Spectating conventions:

- Snapshot, stream and Replay are open to any authenticated Player once a Game is Running (when Builds become visible to all); Open and Cancelled Games answer 409 (`game_not_started`, `game_cancelled`), and the Replay answers `game_not_finished` until the Game is Finished.
- A snapshot is the Replay header plus only the latest Tick. The SSE stream sends a `snapshot` event first, then one `tick` event per Tick after it (event id = Tick), then `end` with the Finished Game, and closes; appending the `tick`s to the snapshot gives the Replay from the moment of joining. A Finished Game's stream is its last snapshot and `end`. A stream that closes without `end` (server restart, or a client too slow to keep up) is reconnected for a fresh snapshot; `Last-Event-ID` is not honoured. The server drops a stream once more than `POSITRONTANKS_MAX_EVENT_STREAM_BUFFER_BYTES` (default 1 MiB) of it is waiting to be sent, so a slow client cannot make an unthrottled Game's Ticks pile up in memory. Idle streams carry a comment line every 15 s.
- Program logs (runtime errors, halts, operations, `log()` output, per run) are served per Game to the owner of the Bots only, filterable by Tick range; they are stored per Player, gzip-compressed, when a Game ends. A Finished Game with no stored Program logs (one Finished before they were kept) answers 404; they are not regenerated.

Paging (every list endpoint: Maps, Bot Designs, Games browse, my Games, Map Revisions, Bot Design Revisions):

- Lists take `?limit=N&cursor=...`. `limit` is an integer from 1 to 200, default 50; anything else is 400 `bad_request`. Leaving both out gives the first page.
- Responses keep their wrapper object (`{"maps": [...]}` and so on) and add `nextCursor`: pass it as `cursor` for the next page; it is null on the last page. Other query parameters (filters) must be repeated on every page.
- Paging is keyset, not offset: a cursor is an opaque token encoding the last item's sort value (`updatedAt`, `createdAt` or Revision number) plus a tie-breaker, so items added, removed or changed while a client pages cause no gaps or duplicates. An item changed mid-walk may move ahead of the pages already read (Maps and Bot Designs are ordered by last change), and so is not seen again in that walk. A malformed cursor, or one from a list with a different kind of order, is 400 `bad_request`.

Auth: username + password at signup (no email in v1); short-lived session tokens; long-lived Player-managed API keys. Player identity is kept separate from credentials so OAuth can be added later.

### Maps API decisions

- **403, not 404, for non-creators.** A Map's existence is public, so a Player who is not its creator and tries to change it (`PATCH`, create Revision, archive, delete a Revision) gets 403 `forbidden`. A Map that does not exist is 404. Bot Designs differ: they are private, so a non-owner gets 404.
- **Creator filter.** `GET /maps?creator=<username>` lists only that Player's Maps; the username matches case-insensitively, and an unknown or malformed one gives an empty list. It combines with `includeArchived`.
- **Order and paging.** `GET /maps` lists matching Maps most recently changed first, paged like every list (see Paging above).
- **Map names** are 1-64 characters after trimming, on create and on `PATCH /maps/{id}`, as for Bot Designs.
- **Renaming** is `PATCH /maps/{id}` (above); it replaces an earlier decision that Maps could not be renamed.
- **Account deletion** is not offered in v1. The foreign keys from Games to Map Revisions and Bot Design Revisions have no delete action, so the database refuses to delete any Revision a Game uses, however the deletion is reached (a Player's Maps and Bot Designs otherwise cascade from the Player). What account deletion does with a Player's content is decided when it is built.

### Games API decisions

- **Access**: every Games endpoint requires authentication (Map reads, by contrast, are public), and any Player may read any Game.
- **Endpoints**: create `POST /games`; browse `GET /games`, Open Games only, newest first, filtered by `rulesetVersion`, `mapId`, `playerCount`, `minPointBudget` and `maxPointBudget`; get `GET /games/{gameId}`; cancel `POST /games/{gameId}/cancel` (Initiator only); submit an Entry `POST /games/{gameId}/entries`; withdraw `DELETE /games/{gameId}/entries/{entryId}` (owner only), which deletes the Entry, freeing its slot and the Revisions it used; "my Games" `GET /players/me/games?state=open,running`, the Games you initiated or entered, in any state unless `state` (comma-separated) is given.
- **Revisions default to the latest**: `mapRevision` on Game create and `revision` on each Entry Bot are optional and default to the latest Revision at that moment. Responses always state the resolved number (the Game's `map.revision`; each own Bot's `design.revision`), and a later Revision never moves an existing Game or Entry.
- **Bot Names**: trimmed, 1-32 characters, no control characters, unique within the Game ignoring case (lower-cased for comparison).
- **Visibility**: while a Game is Open, everyone sees its Entries' Players and Bot Names, but other Players' Builds and costs are hidden; they stay hidden if the Game is Cancelled (it never ran), and are shown to all from Running onward. An Entry's owner always sees its own Builds and costs plus each Bot's design id and Revision. Programs are never shown.
- **Errors**: problems with a new Game (archived Map, unsupported Map Format, unknown Terrains, out-of-range settings) or an Entry (archived, foreign or other-Ruleset Bot Designs, Point Budget, Spawn Zone fit, Bot Names) are all 422 `validation_failed`, every problem listed in `details`. Submitting to, withdrawing from or cancelling a Game that is no longer Open is 409 `game_not_open`, including for the loser of a race for the last slot.
- **Revision deletion** (`DELETE /bot-designs/{id}/revisions/{n}`, `DELETE /maps/{id}/revisions/{n}`): refused with 409 `latest_revision` for the latest Revision, so numbers are never reused, and with 409 `revision_in_use` while any Game in any state (Cancelled included) references it; allowed on archived Bot Designs and Maps.
- **Fill timeout is applied lazily**: there is no background timer. Before every Games request the server cancels each Open Game whose fill deadline has passed (cancel reason `fill_timeout`), recording the deadline itself as `endedAt`, so a Game looks the same whenever it is observed. Known limitation: nothing happens at the deadline itself, so post-v1 webhooks (`game.ended` for a fill timeout) will need an active sweeper.

### Webhooks (post-v1)

One URL per Player; events `game.started` and `game.ended` (covering Finished and Cancelled); payload is the Game ID and event type only, signed with a per-Player secret; retries with backoff.

## 10. Architecture

- **Language**: TypeScript on Node.
- **Repo**: pnpm workspaces: `language`, `engine-r1`, `ruleset-data`, `server`, `cli`, `infra`.
- **Engine** is a pure library (no I/O, no database). Both the server and the CLI runner use it.
- **CLI runner**: `positrontanks run --map <file> --entry <file> ... [--unthrottled]` prints the result and writes a Game Record and Replay. No account, server, or database. Entry file format, defaults and output files: [cli-runner.md](cli-runner.md).
- **Persistence**: SQLite (`node:sqlite`) behind a single data-access module; Litestream replicates to S3. Object storage abstraction (local directory / S3) for Game Records, Replays, and future images.
- **Deployment**: one Docker image. AWS: ECS Fargate (single task, stop-before-start deployments) behind an ALB, S3, provisioned with Pulumi (TypeScript). Runs locally with `docker run`.
- **Testing**: golden Games (fixed Maps, Designs, seeds, expected results) guard frozen engines; unit tests for the language and engine; API integration tests against SQLite.

### Defaults settled in this spec

- Usernames: 3–32 characters, letters, digits, `-` and `_`, case-insensitive unique.
- Map size limits, max time limit, max fill timeout, and concurrent unthrottled Game limit are server configuration values with conservative defaults.
